# Сценарии планирования, общий доступ и менеджерский режим

## Контекст и результат

«Колбаски» остаются редактором одного рабочего плана: фича → роли →
колбаски по спринтам. Дополнение не меняет эту механику. Оно даёт три
отдельных способа пользоваться теми же данными:

1. Владелец создаёт и сохраняет варианты планирования, видит их разницу с
   исходным текущим планом и применяет выбранный вариант осознанно.
2. Команда открывает выданную ссылку после лёгкой регистрации, фильтрует
   команды, меняет только локальный стиль и оставляет привязанные к имени
   комментарии к колбаскам.
3. Менеджмент видит плотную, презентационную шкалу фич по командам: обещанный
   годовой диапазон, фактический диапазон и отклонение без операционных ролей
   и предработ.

Пользовательские задачи успеха:

- за несколько секунд понятно, что изменит предложенный вариант и кого он
  затронет;
- участник извне открывает активную ссылку без Nginx Basic Auth, но не может
  читать или менять бэклог без аккаунта и ссылки;
- менеджер видит сроки бизнеса, а команда — полную фактическую картину;
- интерфейс остаётся спокойным, гладким и объёмным, а не превращается в
  декоративную анимацию.

## Границы первого релиза

Вход: логин (3–32 буквы, цифры, `.`, `_`, `-`) и пароль от 8 символов.
E-mail, подтверждение, приглашения и восстановление пароля не входят в
релиз. Логин отображается как имя автора комментария.

Владелец каждого аккаунта хранит изолированный план. Любой
зарегистрированный пользователь с активной share-ссылкой может открыть
конкретный план в режиме просмотра. Ссылки не открывают список планов и не
дают доступа к API редактирования.

Nginx Basic Auth отключается только в виртуальном хосте
`kolbaski.kzkovich.ru` после проверки конфигурации через `nginx -T`.
Другие server-блоки и проекты не изменяются. Приложение остаётся за HTTPS;
прокси передаёт `X-Forwarded-Proto`, поэтому сессионная cookie имеет флаги
`HttpOnly`, `SameSite=Strict`, `Secure`.

## Сценарии и сравнение

### Модель

Текущий `Plan` — фактический рабочий план. В `Plan.scenarios` хранятся
именованные сохранённые варианты. Каждый вариант содержит:

```ts
interface Scenario {
  id: string;
  name: string;
  createdAt: string;
  updatedAt: string;
  baseSnapshot: ScenarioSnapshot; // неизменяемый исходник на момент создания
  snapshot: ScenarioSnapshot;     // предложенный вариант
}
```

Создание сценария копирует текущие `epics` и `people` в оба снимка. Поэтому
сравнение не меняется, если владелец параллельно отредактировал текущий план.
Старые `Scenario` без `baseSnapshot` нормализуются: их существующий снимок
становится базой, чтобы не потерять данные.

### Экран варианта

Планировщик создаёт «Новый вариант» или открывает уже сохранённый. В верхней
части доступны название, сохранение, дублирование, удаление и переключение
варианта. Запуск автоматического планировщика работает только с открытым
вариантом, никогда напрямую с текущим планом.

Режим сравнения показывает два слоя на одной временной шкале:

- исходная колбаска — приглушённый полупрозрачный керамический контур;
- предложенная колбаска — активный объёмный бар;
- соединительный шлейф и компактная метка показывают перенос влево/вправо;
- добавление, удаление, изменение длительности и изменение команды имеют
  самостоятельные статусы, доступные не только по цвету.

Список изменений группируется по фичам и содержит направление и величину
сдвига в спринтах. Выбор фичи подсвечивает её на обеих шкалах. Применение
сценария выполняется только для отмеченных фич, после подтверждения и
сохранения резервной копии; сам сценарий остаётся сохранённым для повторного
сравнения.

### Фильтрация команд

Один фильтр команд используется в текущем плане, открытом сценарии и экране
сравнения: «Все команды» или одна команда. Он влияет на сетку, список
изменений, агрегаты и менеджерское представление, но не удаляет данные из
сценария. Если фича принадлежит нескольким командам, она показывается при
выборе каждой из них. В сравниваемых агрегатах явно указано, что показано:
например, «Команда AM · 4 из 9 изменённых фич».

## Общий режим команды

### Доступ и права

Владелец создаёт, копирует, отзывает и перевыпускает ссылку. Ссылка содержит
32-байтовый случайный токен; на сервере хранится только SHA-256 хэш. Повторный
выпуск заменяет хэш и сразу инвалидирует прежнюю ссылку.

Маршрут `/share/<token>` требует обычную сессию. Неавторизованный посетитель
попадает на вход/регистрацию и после него возвращается на исходный адрес.
Неверный или отозванный токен выдаёт нейтральную страницу без раскрытия
владельца и существования бэклога.

Все участники с активной ссылкой видят колбаски, baseline и комментарии. Они
не могут переносить, изменять размер, удалять фичи, менять состав команды,
планирование, baseline или настройки общего доступа. Выбранные тема, узор
фона и фильтр команды сохраняются локально в браузере и не меняют план
владельца.

### Комментарии

Комментарий принадлежит `epicId + segmentId`, имеет тип `question`,
`comment` или `issue`, текст, автора, время и статус `open`/`resolved`.
Текст выводится только как текст, без HTML.

Любой участник может создать комментарий. Автор может удалить, закрыть или
переоткрыть свой. Владелец может закрыть, переоткрыть или удалить любой.
События не редактируют план. Если колбаска удалена, комментарии сохраняются
для владельца в истории фичи и не показываются участнику как «висячие».

### API и хранение

Метаданные общего доступа и комментарии не встраиваются в `plan.json`:

```ts
interface ShareState {
  link: { tokenHash: string; createdAt: string; revokedAt: string | null } | null;
  comments: BacklogComment[];
}
```

Они живут рядом с планом конкретного владельца и записываются атомарно.
Маршруты: `GET|POST|DELETE /api/share-link`,
`GET /api/shared/:token/plan`, `GET|POST /api/shared/:token/comments`,
`PATCH|DELETE /api/shared/:token/comments/:id`. Все ответы `no-store`,
мутации требуют сессию, API проверяет владельца по токену, а rate-limit
покрывает генерацию ссылок, чтения и создание комментариев.

## Менеджерский режим

Режим доступен владельцу и через действующую share-ссылку. Он не показывает
роли, загрузку, редактирование или служебные настройки. Сверху — кварталы и
временная сетка; строки сгруппированы по командам. Одна фича — одна компактная
полоса с полным названием в подсказке и понятной текстовой подписью статуса.

Серый керамический контур `plannedFrom → plannedTo` — обещанный бизнесу
диапазон всей фичи. Активная полоса — фактический диапазон, рассчитанный из
сегментов, включённых в менеджерский срок. Если факт начинается/заканчивается
позже baseline, рядом показаны обе даты, например «План: 12.04 · факт:
26.04», а не только тревожный цвет.

```ts
interface ManagementSettings {
  roleDefaults: Record<RoleId, boolean>; // true — учитывать по умолчанию
}

interface Segment {
  managementTiming?: 'inherit' | 'include' | 'exclude';
}
```

Для новых и старых планов все роли включены по умолчанию, кроме ролей с
идентификатором или нормализованным названием `business`/`бизнес` и
`grooming`/`груминг`. Владелец может одним действием изменить правило роли
для всех колбасок. На конкретной колбаске доступно точное переопределение.
В срок попадают только включённые сегменты; отсутствие таких сегментов даёт
только baseline с подписью «Факт не начат». Baseline не меняет загрузку и
детальную фактическую шкалу.

Статусы вычисляются автоматически относительно текущего спринта и baseline:
`Готово`, `В работе`, `Риск`, `Предстоит`. Риск — поздний старт, поздний
финиш либо завершившийся baseline без готовности. Командный цвет остаётся
меткой принадлежности, цвет статуса — отдельной спокойной поверхностью, чтобы
их не смешивать.

## Визуальная система

Новый визуальный слой развивает керамическую тему, но не прячет данные:

- у колбасок — мягкая верхняя грань, приглушённая внутренняя тень, тонкий
  световой кант и понятные состояния hover/focus/drag;
- при переносе исходник остаётся на месте «призраком», а вариант слегка
  приподнят и соединён гладким шлейфом; анимация ограничена transform/opacity;
- шапка, кварталы, фильтры и числовая загрузка получают единый рельеф и
  аккуратную иерархию без градиентного шума;
- в менеджерском режиме уменьшается декоративность: плотная белая поверхность,
  объёмные, но читаемые полосы и высокий контраст дат;
- `prefers-reduced-motion` отключает движения, а клавиатурный focus остаётся
  заметным. Никакая критичная разница не различается только цветом или
  анимацией.

## Компоненты и границы

- `scenarioStore` и `scenarioDiff.ts`: нормализация, сохранение сценариев,
  чистый расчёт изменений и агрегатов;
- `ScenarioWorkspace` / обновлённый `SchedulerCompare`: выбор варианта,
  сравнение, фильтр и безопасное применение выбранных фич;
- `ShareSettingsPanel`, `SharedBacklogPage`, `SegmentCommentsPanel`:
  владелец, read-only маршрут и дискуссия;
- `managementTiming.ts`, `ManagementTimeline`, `ManagementSettingsPanel`:
  чистые правила срока, компактная шкала и глобальные/точечные исключения;
- серверный `shareStore`: токены и комментарии отдельно от пользовательских
  планов.

## Ошибки и проверка

- сохранение сценария, выдача/отзыв ссылки и комментарии показывают понятную
  ошибку; неотправленный текст комментария сохраняется в форме для повтора;
- при конфликте закрытия комментария сервер возвращает актуальную запись;
- сценарий с удалённой в текущем плане фичей остаётся сравниваемым и помечает
  удаление, а не падает;
- до релиза: unit-тесты diff и management timing, API тесты прав автора/
  владельца/другого участника, migration-тесты старых планов, typecheck,
  production build, браузерный сценарий регистрации → share → комментарий →
  отзыв → сравнение → применение;
- деплой: push в `main`, ожидание CI, проверка приложения без Basic Auth,
  HTTPS-cookie, входа, share-ссылки, владельческого редактирования и
  менеджерской шкалы. Перед правкой Nginx — проверить только нужный server
  block и сделать резервную копию его конфигурации.

## Не входит в релиз

E-mail, восстановление пароля, приглашения на конкретную команду, анонимный
доступ, уведомления, вложения, упоминания, треды комментариев, совместное
редактирование сценария и полноценная история версий плана.
